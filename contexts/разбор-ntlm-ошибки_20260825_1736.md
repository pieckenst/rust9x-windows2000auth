# Самое интересное: у тебя подозрительно сломан state machine SSPI

Вот этот кусок Rust-лога меня бы сейчас интересовал **больше всего**:

```text
generate_negotiate_token
...
resetting NTLM state for new authentication sequence
...
AcquireCredentialsHandle
...
InitializeSecurityContext
...
Negotiate token generated (40 bytes)
```

Потом после Type 2:

```text
process_challenge
...
reusing existing credentials handle
...
InitializeSecurityContext (challenge - Type 3)
...
Authenticate token generated (344 bytes)
```

Проблема в том, что NTLM через SSPI — это не просто:

```text
AcquireCredentialsHandle()
ISC(Type1)
ISC(Type2) -> Type3
```

в вакууме.

Нужно сохранять **security context**, созданный первым `InitializeSecurityContext`, и использовать его при втором вызове.

То есть концептуально должно быть:

```text
AcquireCredentialsHandle
        |
        v
InitializeSecurityContext(NULL)
        |
        +----> Type 1
        |
        v
сохранённый CtxtHandle
        |
        | Type 2
        v
InitializeSecurityContext(existing CtxtHandle, Type2)
        |
        v
Type 3
```

А не:

```text
AcquireCredentialsHandle
        |
        v
InitializeSecurityContext(NULL)
        |
        +----> Type 1
             ...
             контекст потеряли / reset
             ...
InitializeSecurityContext(NULL, Type2)
        |
        v
Type 3
```

У тебя логическая структура кода очень похожа на второй вариант.

И особенно настораживает именно:

```text
resetting NTLM state for new authentication sequence
```

Если внутри этого reset уничтожается `CtxtHandle`, а сохраняется только `CredHandle`, то ты фактически пытаешься продолжить NTLM с нового SSPI context.

SSPI может при этом **выдать 344-байтный Type 3**, поэтому Rust считает операцию `SUCCESS`. Это ещё не означает, что получившийся NTLM exchange соответствует тому состоянию, которое сервер ожидает.

# Почему я считаю это более вероятным, чем пароль/domain

Потому что если бы:

```text
username = rsncra
domain   = rust9x
password = ...
```

были просто неправильными, сервер обычно дошёл бы значительно дальше до проверки логонных данных.

А здесь ASP.NET падает на:

```text
Negotiate error code: ClientError
```

то есть ещё на этапе разбора/валидации NTLM authentication message.

ASP.NET Negotiate использует состояние аутентификации, связанное с соединением; Microsoft отдельно подчёркивает, что NTLM credentials/state могут сохраняться между запросами на соединении и что connection affinity для Negotiate важен. citeturn676172search1turn676172search7

означает, что сервер одновременно имеет **полностью мёртвый Redis**.

Но я бы **не считал Redis основной причиной именно `ClientError`**.

Почему:

```text
Type1
  ↓
ASP.NET формирует Type2
  ↓
Type3 приходит
  ↓
NegotiateAuthentication -> ClientError
```

`ClientError` происходит внутри Negotiate/SSPI.

Redis у тебя скорее ломает session/cache/warmup и добавляет многосекундные задержки:

```text
17:08:21  Type1
17:08:33  Redis timeout
17:08:38  session error
17:08:38  Type3
```

Это надо починить отдельно, потому что **30-секундный backlog Redis в процессе NTLM handshake вообще нахрен не нужен**.

Особенно если твой собственный `WindowsAuthMiddleware` зачем-то кладёт промежуточное состояние NTLM в ASP.NET Session. Тогда это уже становится потенциально связанным с authentication state.

У тебя сервер говорит:

И затем:

передаётся **на том же TCP/TLS соединении**:

# Я бы сейчас проверил именно `CtxtHandle`

В твоём `Ntlm` надо найти что-нибудь наподобие:

```rust
pub struct Ntlm {
    credentials_handle: Option<CredHandle>,
    security_context: Option<SecHandle>,
    ...
}
```

или эквивалент.

После первого:

```rust
InitializeSecurityContext(...)
```

должно произойти примерно:

```rust
self.context = Some(new_context);
```

и **этот context нельзя уничтожать между Type1 и Type3**.

При Type2:

```rust
let context = self.context.as_mut().unwrap();

InitializeSecurityContext(
    &credentials_handle,
    context,
    Some(type2),
    ...
)
```

а не новый:

```rust
InitializeSecurityContext(
    &credentials_handle,
    &mut new_context,
    Some(type2),
    ...
)
```

Ты пишешь:

```text

...
```

Но мне надо отдельно увидеть то же самое для **NTLM SSPI context**.

```text

```

а фактически создаёт новый context, это почти наверняка источник проблемы.

Потому что:

```text
CredHandle
```

и

```text
CtxtHandle
```

— это две разные вещи.

`CredHandle` содержит credentials, а `CtxtHandle` — состояние конкретного authentication exchange.

Сохранение только:

```text
credentials_handle = Some(...)
```

недостаточно.

# Есть ещё одна вещь, которую я бы проверил: флаги Type 3

Я посмотрел на начало твоего Type 3.

В одном из токенов получается примерно:

```text
Domain          = rust9x

```

А negotiated flags в Type 3 выглядят примерно как:


Это уже выглядит как полноценный NTLMv2 Type 3, а не какой-то обрезанный пакет.

Причём NT response размером 208 байт очень похож на нормальный NTLMv2 response с AV_PAIR/target info.

Наоборот, SSPI реально генерирует полноценный NTLMv2 authentication blob.

И это опять возвращает нас к состоянию `CtxtHandle` / negotiation state.

# Что я бы сделал первым

### 1. Полностью отключить Redis на время теста

Либо поднять Redis на:

```text
localhost:6379
```

либо временно отключить:

```text
AddStackExchangeRedisCache
UseSession
RedisCacheService
```

чтобы NTLM handshake шёл без параллельного:

```text
RedisConnectionException
```

Это устранит шум и исключит потерю auth/session state.

---

### 2. На стороне Rust залогировать существование NTLM context

Перед Type1:

```text
credentials_handle: NONE
security_context: NONE
```

После первого `InitializeSecurityContext`:

```text
credentials_handle: SOME
security_context: SOME
status: SEC_I_CONTINUE_NEEDED
```

Перед Type3:

```text
credentials_handle: SOME
security_context: SOME
```

После Type3:

```text
security_context: SOME
status: SEC_I_COMPLETE_NEEDED / SEC_E_OK
```

Если перед Type3:

```text
security_context: NONE
```

— вот и практически найден баг.

---

### 3. Не делать reset context между Type1 и Type3

Вот это:

```text
resetting NTLM state for new authentication sequence
```

должно происходить **только перед новым HTTP authentication exchange**.

Но не между:

```text
Type1 → Type2 → Type3
```

---

### 4. Сравнить с эталонным клиентом

На той же машине сделать запрос через обычный .NET client:

```csharp
var handler = new HttpClientHandler
{
    Credentials = new NetworkCredential(
        "rsncra",
        "password",
        "rust9x")
};

using var client = new HttpClient(handler);

var response = await client.GetAsync(
    "https://localhost:5001/api/v1/auth/windows/windows-login");
```

И посмотреть server log.

Если:

```text
.NET HttpClient → Type1 → Type2 → Type3 → 200
```

а:

```text
Rust SSPI → Type1 → Type2 → Type3 → 400 ClientError
```

то сервер практически автоматически становится контрольной группой: проблема именно в формировании/сохранении NTLM state в твоём Rust wrapper.

# И ещё: server-side `ClientError` надо раскрыть

Сейчас ты логируешь:

```text
Negotiate error code: ClientError.
The users authentication request was invalid.
```

Но тебе нужен **внутренний Win32 HRESULT/error code**.

Добавь вокруг вызова `NegotiateAuthentication` что-нибудь вроде:

```csharp
catch (Win32Exception ex)
{
    logger.LogError(
        ex,
        "Negotiate failed. ErrorCode=0x{Code:X8}, NativeErrorCode={Native}",
        ex.HResult,
        ex.NativeErrorCode);
}
```

Именно там мы хотим увидеть:

```text
0x80090308
SEC_E_INVALID_TOKEN
```

Если он действительно там — это практически окончательное подтверждение, что ASP.NET не считает Type 3 валидным NTLM message, а не просто отвергает пароль.

Такой `ClientError` с `0x80090308` встречается именно как «The token supplied to the function is invalid». citeturn685401search0turn685401search1

## Мой текущий диагноз

По вероятности я бы поставил так:

| Причина | Вероятность |
|---|---:|
| Rust NTLM `CtxtHandle` не сохраняется/не используется между Type1 и Type3 | **очень высокая** |
| Собственный middleware теряет NTLM state между запросами | **высокая** |
| Redis/session ломает state или создаёт задержки | **средняя** |
| Неправильный domain/password | низкая для именно `ClientError` |
| TLS/SNI/сертификат | практически ноль |
| HTTP keep-alive / новый connection | низкая — лог показывает reuse |

Самое главное: **ты уже прошёл самый мерзкий участок TLS/Schannel. Сейчас это выглядит не как проблема Windows 10 Schannel вообще, а как чистая проблема NTLM SSPI state machine.**

И отдельно: `401` после Type1 — **нормальный результат**, `401` после первого Type3 с `ClientError` — уже нет. Kestrel действительно использует `WWW-Authenticate: Negotiate` для NTLM; сам факт, что сервер декодировал твой первый пакет как NTLM Type1 и сформировал Type2, подтверждает, что формат первого пакета нормальный. citeturn676172search7
